# What a stop hook can do under Claude Code, measured

> Measured on 2026-10-08 on Windows 11, Node v24.19.0, tool version 2.1.293, with the repo at
> commit `8d82806` on branch `worktrees`. Findings, not instructions. Every run was a HEADLESS
> session (`claude -p`, stream output); no interactive session was watched.

## 1. The method

A throwaway git repo in the session scratchpad held one settings file registering a probe
script for the `Stop` event, with the project-directory variable spelled with braces. The probe
appended each payload it was handed to a log and answered in the way a mode file named. One
session per mode, each with the prompt "Reply with the single word ok. Use no tools." The
stream output of each session was kept and read for what the person and the model were shown.

## 2. The payload

Every stop payload carried these keys: `session_id`, `transcript_path`, `cwd`, `prompt_id`,
`permission_mode`, `effort`, `hook_event_name`, `stop_hook_active`, `last_assistant_message`,
`background_tasks`, `session_crons`. `hook_event_name` was `Stop`. `stop_hook_active` was the
boolean `false` on the first stop of a turn in all six sessions.

## 3. What each answer did

| The hook's answer | Turns | What the stream showed |
|---|---|---|
| exit 0, `{"systemMessage": "..."}` on stdout | one | a `system` event, level `notice`, content `Stop says: ` and the message; the turn ended |
| exit 0, text on stderr, nothing on stdout | one | nothing: the text reached nobody |
| exit 2, text on stderr, nothing on stdout | one | a notification `Stop hook error occurred`; NO further turn. Run twice, same result |
| exit 0, `{"decision": "block", "reason": "...", "systemMessage": "..."}` | two | the reason reached the model as a user message `Stop hook feedback: ` and the reason; the model did what it said; the notice was shown too |
| exit 2, the same `decision: block` JSON on stdout, text on stderr | two | as the row above: the JSON was read at exit 2 and the reason in it, not the stderr text, reached the model |

## 4. A first stop against a forced one

In both sessions that forced a turn the probe was called twice. The first payload carried
`stop_hook_active: false` and the second `stop_hook_active: true`. Nothing else in the key set
differed. A handler that forces a turn only when that field is not `true` therefore forces at
most one turn per stop, which is what the two sessions did: each ended after its second turn.

## 5. What this does and does not establish

- A report that must not force a turn is a `systemMessage` at exit 0. Stderr at exit 0 is lost.
- A forced turn is `decision: block` with a `reason`. Spelled with exit 2 as well it still
  forces, so the entry's rule that a deny leaves with exit 2 holds at stop.
- Exit 2 with stderr alone did not force a turn here. The dialect spelled a stop deny that way
  before this measurement, so until it changes a stop handler's deny forces nothing.
- Not measured: an interactive session, where the notice is rendered by the terminal UI; the
  two other registry rows that share the `claude` wire format; a stop hook that times out.
